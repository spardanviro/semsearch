# 阶段 1.5 报告：评测集与混合检索

日期：2026-11-02

## 结论
- 新增评测集（54 条查询）和打分脚本 `evals/run.py`，以后改分块或检索策略都能用数字判断效果。
- 新增 FTS5 关键词索引。默认检索模式改为 **hybrid**：查询里有标识符形状的词时，在余弦分上加一个小的 BM25 加分；其余查询仍是纯向量。
- 收益很小：54 条里只有 5 条名次变了。混合检索多找到 2 条（含一条纯向量完全找不到的），另有 3 条掉了一名（都还在前 3）。整体 R@5 从 0.796 升到 0.815，MRR 基本不变（0.698 → 0.690）。
- 原因：分块时符号名已写进块头一起嵌入，EmbeddingGemma 对标识符本来就很敏感。关键词只在"确切名字只出现在代码体里"时有用，比如函数体里用到的常量 `CREATE_BREAKAWAY_FROM_JOB`。
- 代价可以忽略：RaftMod-Publish 上关键词索引 1.3 MB（占索引约 8%），关键词查询约 1 ms。
- 需要时可以用 `SEMSEARCH_SEARCH_MODE=vector` 退回纯向量。

## 实现
- `index/keywords.py`：把标识符拆成词（`getPlayerInventory` → getplayerinventory / get / player / inventory），只处理 ASCII 词；`has_identifier()` 判断查询里是否有 camelCase、snake_case、全大写或字母加数字的词。
- `chunks_fts`：contentless FTS5 表（`contentless_delete=1`），rowid 与 `chunks.id` 相同，分 meta（路径 + 符号名）与 body 两列，BM25 权重为 2 : 1。
- `search.boost()`：最终分数 = 余弦 + λ × BM25 / 本次查询最高 BM25。显示给用户的分数始终是余弦相似度。
- 关键词侧出错（SQLite 异常）时退回纯向量，不影响检索。
- 带路径或类型过滤时，BM25 结果是先排序再过滤；剩下的不够时会逐步扩大读取范围，上限 2 万行，避免窄过滤把关键词命中全部丢掉。
- 依赖 SQLite 3.43 及以上版本（`contentless_delete`）。uv 的 Python 3.12 自带 3.49 / 3.50，满足要求。
- 代码审查（无严重问题）后修了以下几处：`HTTPServer` 这类以缩写开头的名字没被识别为标识符；`3rd`、`10px` 这类数字开头的词误触发混合检索；窄过滤会丢掉关键词命中；`SEMSEARCH_KEYWORD_WEIGHT` 没有输入校验。每处都补了回归测试。
- 升级说明：schema 版本升到 3，已有索引第一次打开时会自动重建（RaftMod-Publish 约 1.5 分钟）。meta 中新增 `keywords_version`，以后修改分词规则会触发重建。

## 还没解决的问题
- **中文概念查询仍是短板**：MRR 0.59，英文为 0.82。漏检的大多是中文描述配英文代码，靠关键词解决不了。可以考虑的方向：
  - 在 subagent 里把中文问题改写成英文再查一次（路由规则里已经建议这样做）；
  - 改进块头：加上注释摘要，或者给每个块生成一句描述，成本较高；
  - 试 EmbeddingGemma 的其他 prompt 组合。
- 每个文件最多返回 2 条结果，同一文件里排在后面的正确块会被挤掉，`CREATE_BREAKAWAY_FROM_JOB` 就是这个原因。可以评估放宽到 3 条。
