# 阶段 1.5 报告：评测集与混合检索

日期：2026-11-02

## 结论
- 新增评测集（54 条查询）和打分脚本 `evals/run.py`，以后改分块或检索策略都能用数字判断效果。
- 新增 FTS5 关键词索引。当时默认检索模式改为 **hybrid**：查询里有标识符形状的词时，在余弦分上加一个小的 BM25 加分；其余查询仍是纯向量。（后续：分块器 v4 之后，hybrid 不再有收益，默认已改回纯向量，见 `docs/EVAL_REAL_PROJECTS.md`。）
- 收益很小：54 条里只有 5 条名次变了。混合检索多找到 2 条（含一条纯向量完全找不到的），另有 3 条掉了一名（都还在前 3）。整体 R@5 从 0.796 升到 0.815，MRR 基本不变（0.698 → 0.690）。
- 原因：分块时符号名已写进块头一起嵌入，EmbeddingGemma 对标识符本来就很敏感。关键词只在"确切名字只出现在代码体里"时有用，比如函数体里用到的常量 `CREATE_BREAKAWAY_FROM_JOB`。
- 代价可以忽略：RaftMod-Publish 上关键词索引 1.3 MB（占索引约 8%），关键词查询约 1 ms。
- 需要时可以用 `SEMSEARCH_SEARCH_MODE=vector` 退回纯向量。

## 实现
- `index/keywords.py`：把标识符拆成词（`getPlayerInventory` → getplayerinventory / get / player / inventory），只处理 ASCII 词；`has_identifier()` 判断查询里是否有 camelCase、snake_case、全大写或字母加数字的词。
- `chunks_fts`：contentless FTS5 表（`contentless_delete=1`），rowid 与 `chunks.id` 相同，分 meta（路径 + 符号名）与 body 两列，BM25 权重为 2 : 1。
- `search.boost()`：最终分数 = 余弦 + λ × BM25 / 本次查询最高 BM25。显示给用户的分数始终是余弦相似度。
- 关键词侧出错（SQLite 异常）时退回纯向量，不影响检索。
- 带路径或类型过滤时，BM25 结果是先排序再过滤；剩下的不够时会逐步扩大读取范围，上限 2 万行，避免窄过滤把关键词命中全部丢掉。
- 依赖 SQLite 3.43 及以上版本（`contentless_delete`）。uv 的 Python 3.12 自带 3.49 / 3.50，满足要求。
- 代码审查（无严重问题）后修了以下几处：`HTTPServer` 这类以缩写开头的名字没被识别为标识符；`3rd`、`10px` 这类数字开头的词误触发混合检索；窄过滤会丢掉关键词命中；`SEMSEARCH_KEYWORD_WEIGHT` 没有输入校验。每处都补了回归测试。
- 升级说明：schema 版本升到 3，已有索引第一次打开时会自动重建（RaftMod-Publish 约 1.5 分钟）。meta 中新增 `keywords_version`，以后修改分词规则会触发重建。

## 中文查询改进（第二轮）

### 漏检原因（逐条看了中文概念查询的排序）
1. **跨语言匹配本身偏弱**：查询是中文描述，代码是英文。
2. **中文文档排在代码前面**：RaftMod 的《全局审校报告》和 CHANGELOG 用中文写的正是同一批功能，和中文查询最像（相似度 0.81 以上）。
3. **分数挤在一起**：前几十名都在 0.72–0.83 之间，区分度低。

### 试过的方案（hybrid 模式，54 条）
| 方案 | 中文类 MRR | 全部 MRR | 结论 |
|---|---|---|---|
| 现状（SearchQuery 提示词） | 0.583 | 0.690 | 基线 |
| 查询提示词换成 QuestionAnswering | 0.561 | 0.665 | 更差 |
| 查询提示词换成 CodeRetrieval | 0.523 | 0.673 | 更差 |
| 查询提示词换成 FactChecking | 0.543 | 0.665 | 更差 |
| 每个文件最多 3 条结果 | 0.582 | 0.695 | R@5 0.815 → 0.833，提升在噪声范围内，未采用 |
| 同一个长方法的多段只占一个名额 | 0.583 | 0.690 | 没有变化，已撤销 |
| **中文问题先翻成英文再查** | **0.700** | **0.751** | 采用 |

翻译用的是另一个没看过代码的模型盲译的结果（`evals/cases/translations_en.json`），避免翻译时用词贴近代码里的名字。只看 22 条中文概念查询：R@5 从 0.64 升到 0.86。同时用中文和英文查、取较高分，效果不如只用英文。

### 怎么落地
调用检索的是 Claude，翻译对它几乎没有成本，所以改的是会影响 Claude 怎么写查询的所有地方：
- MCP 服务说明和 `semantic_search` 工具说明：要求 query 一律用英文写，非英文问题先翻译；
- `semantic-search` subagent：第一步就用英文查，只有项目注释或文档本身是该语言时才用原语言查；
- CLAUDE.md 路由规则：语义检索的 query 一律用英文；
- 兜底：查询里出现中日韩或西里尔文字时，检索结果末尾提示"用英文重查效果更好"，命令行使用时也能看到。

验证方法：`uv run python evals/run.py --modes "hybrid,hybrid;tr=1"`，其中 `tr=1` 把中文查询换成对应的英文翻译。
